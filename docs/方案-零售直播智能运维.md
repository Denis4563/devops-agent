# GameDay「Agent to the Rescue」
# 零售直播大促：DevOps Agent 驱动的场景化智能运维方案

> 配置数值为演示环境的预估值。DevOps Agent 的功能、价格和配额以官方文档及《AWS DevOps Agent 介绍（中文）.pptx》《AWS_DevOps_Agent_MSP_Partner.pptx》为准。

---

## 1. 方案概述

### 1.1 业务背景
一家跨境零售电商，面向 **新加坡（SG）** 和 **欧洲（EU）** 两个市场，每周开直播大促（约 2 小时，含限量券和爆款秒杀）。业务部署在 **ap-southeast-1（新加坡）**，通过 CloudFront 向两个市场交付。

### 1.2 三大运维诉求
| # | 诉求 | Agent 要做出的关键判断 |
|---|---|---|
| S1 | 按业务链路分阶段扩缩容 | 结算饱和、数据库有余量 → **只扩结算**；爆款锁争用 → **不扩容，改为排队** |
| S2 | 按地区匹配 CloudFront 交付 | 只有 EU 变慢 → 是**追踪参数拆散了缓存**，不是容量不足 |
| S3 | 按风险等级启停额外防护 | 流量涨得快 ≠ 攻击 → 正常抢券**不启用防护**；确认异常后**只限领券接口** |

### 1.3 Demo 定位
- 3 人、1 天搭建完成，10 分钟演示。
- 业务服务用 nginx 模拟，业务指标由脚本推送。演示重点是 **Agent 的判断能力和运维闭环**。
- 闭环核心是 **ops-mcp**：Agent 通过它读取业务上下文、把诊断结论写回 Jira、提交执行请求。
- 闭环：**告警 → Jira 建单 → DevOps Agent 调查 → ops-mcp 回写结论并提交执行请求 → Jira 审批 → GitHub 执行 → Jira 回写 + 飞书通知**。

## 2. 为什么需要 DevOps Agent（对比常规 DevOps 运维）

### 2.1 常规 DevOps 运维在直播大促中的痛点
| 痛点 | 常规做法 | 后果 |
|---|---|---|
| 告警多、信息散 | 值班人员在 CloudWatch、kubectl、CloudFront 日志、WAF 控制台、GitHub 之间来回切换 | 定位慢；大促窗口只有 1–2 小时 |
| 自动扩缩容只看单一指标 | HPA 按 CPU/请求数扩容 | **锁争用时继续加机器**，加剧争用、浪费成本 |
| 地区性问题容易误判 | 看到"EU 慢"就扩容或归因于跨区延迟 | 真正原因（缓存键被追踪参数拆散）没被发现 |
| 防护策略一刀切 | 流量突增就整体收紧 WAF | 误伤正常抢券用户，下单和支付也被限流 |
| 经验在个人脑子里 | 资深 SRE 凭经验判断 | 换人值班就退化；凌晨或周末更慢 |
| 复盘依赖人工 | 事后人工写复盘 | 改进项难以落地，同类问题反复发生 |

### 2.2 能力对比
| 维度 | 常规 DevOps 运维 | 规则式自动化（HPA/告警+脚本） | DevOps Agent 方案 |
|---|---|---|---|
| 数据关联 | 人工跨工具查看 | 只看配置好的单一指标 | 自动关联指标、日志、kubectl、拓扑、GitHub 变更，并通过 ops-mcp 读取业务上下文 |
| 根因判断 | 依赖个人经验 | 无（只会触发动作） | 多假设并行 + **反证排除**，给出置信度 |
| 业务语义 | 靠人理解活动阶段 | 无 | 通过 **Skill** 预置三阶段模型和判定规则 |
| "不该做什么" | 依赖经验 | **做不到**（规则只会扩） | 能给出"不扩容""不启用防护"的结论 |
| 响应时间 | 30–60 分钟定位（官方客户数据平均 42 分钟） | 秒级执行，但可能执行错 | 约 5–8 分钟出结论（官方：42→8 分钟/事件） |
| 7×24 一致性 | 受值班人员水平影响 | 一致但死板 | 一致，并可持续迭代 Skill |
| 变更治理 | 人工操作，留痕不完整 | 脚本自动执行，缺少审批 | Agent 提交请求 → Jira 审批 → GitHub 执行，配合不可变调查日志，全程留痕 |
| 持续改进 | 人工复盘 | 无 | Prevention 建议（可观测性/测试/代码韧性/基础设施） |
| 引入成本 | 人力 | 低 | 按使用计费，无座位费 |

### 2.3 Agent 与现有工具的关系
DevOps Agent **不替代**现有监控、HPA 和 WAF，而是位于"告警之后、变更之前"的**调查与决策层**：
- CloudWatch 告警负责发现异常；
- DevOps Agent 负责回答"为什么、该不该动、动哪里"；
- ops-mcp 负责把 Agent 的判断转成可审批的执行请求；
- GitHub Actions Runbook 负责按审批结果可靠执行；
- Jira/飞书负责记录和协同。

### 2.4 用来证明必要性的 3 个"反直觉"时刻
| 时刻 | 常规运维/规则自动化的反应 | Agent 的判断 |
|---|---|---|
| S1-b 爆款锁争用 | 延迟高 → 扩容 | 结算 CPU 不高、锁等待集中在单一 SKU → **不扩容，排队** |
| S2 EU 变慢 | 扩容或归因于跨区延迟 | 只有 EU 命中率暴跌、回源暴增 → **修缓存键** |
| S3-a 抢券高峰 | 流量暴涨 → 收紧防护 | 放券窗口内、成功率正常 → **不启用防护** |

## 4. 场景 S1：分阶段扩缩容

### 4.1 三阶段流量模型（Skill 预置）
| 阶段 | 时间 | 主要压力 | HPA（min/max） |
|---|---|---|---|
| WARMUP 预热 | 开播前 30 分钟 | 浏览 → catalog | catalog 4/12，checkout 2/4，coupon 2/4 |
| PEAK 开卖 | 开播后 60 分钟 | 领券、下单 → coupon/checkout | catalog 3/8，checkout 4/20，coupon 4/16 |
| TAIL 尾单 | 下播后 90 分钟 | 支付确认 | catalog 2/4，checkout 2/6，coupon 1/2 |
| NORMAL | 尾单回落后 | — | catalog 2/4，checkout 2/4，coupon 1/2 |

阶段由 ops-mcp 的 `get_campaign_context` 提供（SSM 参数 `/retail-live/campaign/current`：开播时间、阶段、爆款 SKU、放券时间），同时推送 `Phase` 指标（0=NORMAL，1=WARMUP，2=PEAK，3=TAIL）。**Agent 以指标为准，活动日历只作为先验。**

### 4.2 Demo 用例
| 用例 | 模拟数据 | Agent 预期结论 | 提交的执行请求 |
|---|---|---|---|
| S1-a 结算饱和 | PEAK；checkout CPU 85%、InFlight 45/Pod、HPA 已到 max 4；DB CPU 40% | 只扩 checkout | `scale {"svc":"checkout","min":4,"max":20}` |
| S1-b 爆款锁争用 | checkout P95 1200ms 但 CPU 35%；`SkuLockWaitMs{SKU=HOT-001}`=800ms | **不扩容**，建议对 HOT-001 排队 | 不提交执行请求，只写 Jira 评论"不建议扩容" |
| 收尾撤容 | TAIL→NORMAL，积压回落 | 恢复 NORMAL 容量 | `scale {"svc":"checkout","min":2,"max":4}` |

## 5. 场景 S2：SG / EU 地理交付

### 5.1 交付设计
| 路径 | 缓存策略 | 说明 |
|---|---|---|
| `/live/*` | 缓存键：Path + `CloudFront-Viewer-Country`；Query String 只放行 `sku`、`lang` | CF Function `geo-rewrite`：SG→`/sg/`，EU 国家→`/eu/`，其他→`/sg/`；剥离 `utm_*`、`live_trace_id`、`fbclid`、`ttclid` |
| `/sg/*`、`/eu/*` | TTL 1 天 | 静态页面和素材 |
| `/api/cart`、`/api/order`、`/api/pay`、`/api/coupon` | CachingDisabled | 购物车和结算不走公共缓存 |

EU 国家（初值，待确认）：DE、FR、NL、BE、IT、ES、IE、AT、PL、SE、DK、FI、PT。

### 5.2 Demo 用例
| 用例 | 模拟/注入 | Agent 预期结论 | 提交的执行请求 |
|---|---|---|---|
| S2 缓存被拆散 | 修改 CF Function，让 EU 分支不剥离 `live_trace_id`；curl 带随机参数；模拟 EU CacheHitRate 92%→35%、回源量 ×6，SG 正常 | 追踪参数拆散缓存；**排除容量不足和跨区延迟** | `cdn_fix {}`（恢复 CF Function + invalidation） |

## 6. 场景 S3：分级防护

### 6.1 WAF 规则
| 规则 | 状态 |
|---|---|
| IP 信誉 / 通用规则 / 已知恶意输入（托管规则） | 常开 Block |
| `coupon-claim-rate-guard`：仅 `/api/coupon/claim`，每 IP 100 次/60 秒 | 默认 Count，L2 时切到 Block |
| 下单、支付接口 | 不加额外限速 |

### 6.2 风险分级（Skill 预置，阈值待确认）
| 等级 | 条件 | 动作 |
|---|---|---|
| L0 正常 | 放券窗口内，成功率 >85%，重复提交 <3% | 不启用防护 |
| L1 关注 | 成功率 60–85% 或重复提交 >10% | 保持 Count，Jira 评论 + 飞书提醒 |
| L2 异常 | 成功率 <60% 且重复提交 >25%，或 WAF Count >5000/分钟 | 提交 `waf_guard {"mode":"on"}`（仅领券接口） |
| 回落 | 拦截 <100/分钟持续 10 分钟 | 提交 `waf_guard {"mode":"off"}` |

### 6.3 Demo 用例
| 用例 | 模拟数据 | Agent 预期结论 | 提交的执行请求 |
|---|---|---|---|
| S3-a 正常抢券 | 放券窗口内，领券 QPS ×10，成功率 92%，重复提交 1% | **不启用防护** | 不提交 |
| S3-b 刷券 | 成功率 45%，重复提交 35%，WAF Count 8000/分钟 | 只对领券接口限速 | `waf_guard on` → 回落后 `off` |

## 7. 运维闭环与 ops-mcp

### 7.1 端到端流程
```
① simulate.py 推送指标 → 告警 → SNS → jira-bridge /alarm → Jira 建单（状态：待诊断）
② Jira Automation（创建时）→ jira-bridge /investigate → HMAC 签名调用 Agent Webhook
③ Agent 调查：加载 Skill → 调 ops-mcp 读活动上下文和业务指标 → 读 CloudWatch / kubectl / GitHub
④ Agent 调 ops-mcp：
     jira_comment：结论、证据、已排除的假设
     request_runbook：参数白名单校验通过后填写 Runbook 字段，工单流转到"待审批"
     （结论为"不扩容""不启用防护"时只写评论，工单流转到"已完成"）
⑤ EventBridge Investigation Completed → agent-notify → 飞书卡片（结论 + Jira 审批链接）
⑥ 审批人在 Jira 流转"已批准"
⑦ Jira Automation → GitHub repository_dispatch
⑧ GitHub Actions：调 Jira API 校验状态=已批准、参数与工单一致 → 执行 Runbook → 回写 Jira → 工单流转"已完成" → 飞书通知
```

### 7.2 ops-mcp 工具清单
| 工具 | 类型 | 说明 |
|---|---|---|
| `get_campaign_context` | 只读 | 当前活动、阶段、开播时间、爆款 SKU、放券时间（读 SSM） |
| `get_business_metrics(scenario, minutes)` | 只读 | 按场景返回 RetailLive 指标的最新值和变化：S1 结算/DB/锁等待，S3 领券成功率/重复提交/WAF Count |
| `get_cdn_market_breakdown(minutes)` | 只读 | 按 SG/EU 返回命中率、回源量、回源延迟，并对比基线 |
| `get_runbook_catalog` | 只读 | 返回可用 Runbook、参数及取值范围（读仓库 `config/runbooks.yaml`） |
| `jira_comment(jira_key, body)` | 写记录 | 写诊断结论（Markdown 模板） |
| `request_runbook(jira_key, runbook, params)` | 写记录 | 白名单校验后写入 `Runbook`、`Runbook Params` 字段，流转到"待审批"；**不触发执行，也不能审批** |

设计要点：
- ops-mcp **不直接修改任何 AWS 资源**，写操作只到 Jira，执行必须经过人工审批。这符合官方"MCP 只暴露必要工具、工具白名单"的建议。
- 认证：Agent Space 中注册为 MCP Server，使用 API Key；nginx 提供 HTTPS（ACM + ALB，或域名 + Let's Encrypt）。
- 实现：Python FastMCP，固定 `mcp<2`；传输优先 SSE，nginx 设置 `proxy_read_timeout 3600s`、关闭缓冲；注册时以 Agent Space 支持的传输方式为准，搭建当天上午先验证连通。
- Jira 使用 `devops-agent-bot` 账号，只能评论、改字段、流转到"待审批"/"已完成"。

### 7.3 Jira 设计
| 项 | 设计 |
|---|---|
| 项目 | `LIVEOPS` |
| 字段 | `Scenario`（S1/S2/S3）、`Phase`、`Market`、`Runbook`（scale / cdn_fix / waf_guard）、`Runbook Params`（JSON）、`Agent Investigation URL` |
| 工作流 | 待诊断 → 待审批 → 已批准 → 已完成；分支：已驳回 |
| 审批条件 | "待审批 → 已批准"仅限 `approvers` 组 |
| Automation | ① 创建时 → jira-bridge `/investigate`；② 已批准时 → GitHub `repository_dispatch` |

### 7.4 治理
| 环节 | 控制措施 |
|---|---|
| Agent 权限 | EKS Access Entry 只读；不启用指示型操作 |
| ops-mcp | 只写 Jira；参数白名单；API Key 存 Secrets Manager |
| 审批 | 仅 `approvers` 组；bot 账号无审批权 |
| 执行 | GitHub OIDC 最小权限；执行前二次校验 Jira 状态和参数；支持 `DRY_RUN` |
| 留痕 | Agent 不可变调查日志 + Jira 评论 + GitHub Actions 日志 + CloudTrail |

## 10. 风险与限制
| 风险/限制 | 应对 |
